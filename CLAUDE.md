# Money Manager

Личное приложение для учёта денег: доходы, «копилки» с процентным распределением, канбан-доска расходов по дням, переливы между копилками, долги в обе стороны, история действий с отменой, статистика.

Задача ставилась и уточнялась в чате пошагово — этот файл фиксирует итоговое состояние и принятые решения, чтобы не передоказывать их заново в следующих сессиях.

## Стек и структура

Монорепо на npm workspaces, два пакета:

- `back/` — NestJS 11 + Prisma **7** (важно, см. ниже) + PostgreSQL. REST API, глобальный префикс `/api`.
- `front/` — Nuxt 4 + Nuxt UI v4 + Pinia + VueUse + Chart.js (`vue-chartjs`).

Корневой `package.json` только описывает workspaces и пробрасывает dev/build-скрипты (`dev:back`, `dev:front`, `build:back`, `build:front`).

**Git:** локальный репозиторий инициализирован в корне (`money-manager/`, не в `back/`), но **ни одного коммита ещё не сделано** и никуда не запушено — всё изменения существуют только на диске. Не считай, что где-то есть удалённая копия.

## Локальный запуск

```bash
docker start money-manager-db   # Postgres в докере (если контейнера нет — см. ниже)
npm run dev:back                # http://localhost:3000/api
npm run dev:front               # http://localhost:3002 (порт менялся, проверяй nuxt.config.ts)
```

Если контейнера `money-manager-db` ещё нет:
```bash
docker run -d --name money-manager-db \
  -e POSTGRES_USER=money_manager -e POSTGRES_PASSWORD=money_manager -e POSTGRES_DB=money_manager \
  -p 5432:5432 postgres:16-alpine
cd back && npx prisma migrate dev
```

`back/.env` (не в гите) содержит `DATABASE_URL`, `DIRECT_URL` (обе указывают на локальный докер), `JWT_SECRET`, `CORS_ORIGIN`. Смотри `back/.env.example` и `front/.env.example` за актуальными ключами — **порт фронта и `CORS_ORIGIN` уже правились руками пользователя минимум один раз, не полагайся на цифры из старых сообщений чата, перечитай файлы**.

Оба dev-сервера сейчас **остановлены** (последнее действие в сессии — `pkill` + `docker stop`). Контейнер не удалён, данные (тестовый юзер, копилки, история) сохранены.

## Доменная модель и бизнес-логика (самое важное)

### Копилки (`Jar`)

- Поле `type: SPENDING | SAVINGS` (enum `JarType`).
  - **SPENDING** («Расходная») — обычная копилка, можно тратить.
  - **SAVINGS** («Накопительная») — деньги откладываются и **не считаются доступными к тратам**.
- Доход по умолчанию распределяется между **всеми** активными копилками (обоих типов) по `defaultPercent` — сумма процентов активных копилок всегда должна давать 100%.
- При создании/изменении процента одной копилки остальные **автоматически пропорционально ужимаются** (см. `JarService.rebalanceOthers` в `back/src/jar/jar.service.ts`). При архивации копилки её процент так же пропорционально раздаётся остальным.
- **SAVINGS-копилки нельзя:**
  - использовать как колонку на канбан-доске расходов (нет в списке колонок, `BoardService` кидает 400 при попытке);
  - использовать как источник ни в одном направлении долга (`DebtService` фильтрует `type: SPENDING` при валидации аллокаций).
- **SAVINGS-копилки можно:** пополнять и опустошать через переливы (`Transfer`) в обе стороны — это единственный способ ими управлять руками, кроме автораспределения дохода.
- Цвет копилки — произвольный hex (палитра из 10 пресетов в `JarForm.vue`, без нативного `input[type=color]`). Используется на карточках, в колонках канбана и **в круговой диаграмме статистики** (`statistics.vue` берёт `jar.color` из стора, а не generic-палитру).
- Дашборд и `/jars` показывают **два отдельных тотала**: «Доступно к тратам» (сумма SPENDING) и «Накоплено» (сумма SAVINGS) — не складывать вместе.

### Доход (`Income`)

- Создаёт `Income` + `IncomeAllocation[]`, распределяет сумму по копилкам либо по `defaultPercent`, либо по ручному override из формы (переключатель «Разделить по копилкам вручную»).
- Округление: последняя аллокация в списке получает остаток от суммы, чтобы не терять копейки из-за округления (см. `IncomeService.distributeAmount`).

### Канбан-доска расходов (`Month` → `Day` → `Expense`)

- `Month`/`Day` создаются лениво (find-or-create) при первом расходе на дату — календарь не предгенерируется.
- Колонки = активные копилки типа **SPENDING** (`jarsStore.spendingJars`, не `activeJars`).
- Даты обрабатываются **без привязки к локальной таймзоне** — сравнение идёт по `yyyy-mm-dd`-строкам напрямую (`toISODate(year, month, day)` в `board/[year]/[month].vue`), а не через `new Date(y,m,d).toISOString()`. Это специально: сервер тестировался в UTC+5, и локальная конструкция даты сдвигала день на -1 при переводе в UTC. **Не переписывай на `Date`-арифметику с локальной таймзоной, это был реальный баг.**
- Drag-n-drop между колонками — VueUse `useSortable` (обёртка над SortableJS), группа `board-columns`, координация через `data-jar-id`/`data-expense-id` атрибуты в `KanbanColumn.vue`. Перенос карточки между копилками = кредит старой копилке + дебет новой в одной операции.

### Долги (`Debt`) — асимметричная логика, легко перепутать

Два типа (`DebtType`): `OWED_TO_ME` («мне должны») и `I_OWE` («я должен»). Балансовая семантика **разная**:

| | При создании | При погашении/возврате | При «простить» |
|---|---|---|---|
| **OWED_TO_ME** (дал в долг) | Списывается сразу с выбранных копилок (деньги реально ушли) | Зачисляется обратно в копилки | Списание остаётся — деньги не возвращаются |
| **I_OWE** (взял в долг) | Баланс **не меняется** — это только план, куда пойдёт погашение | Списывается с копилок только в этот момент (деньги реально уходят) | Ничего не списывается — оплата не потребуется |

- Обе стороны при создании и при погашении обязаны распределять сумму **только по SPENDING-копилкам** (проверка в `DebtService.create`/`repay`).
- Погашение без явной ручной разбивки использует **ту же пропорцию**, что была задана при создании долга (`DebtService.proportionalSplit`).
- Статусы: `ACTIVE` → `PARTIALLY_REPAID` → `REPAID`, либо в любой момент → `FORGIVEN`.
- UI (`debts.vue`): закрытые долги (`REPAID`/`FORGIVEN`) **скрыты по умолчанию** — есть переключатель «Показывать закрытые (N)», чтобы не путать пользователя карточками с суммой 0. Кнопка «Простить» — прямое действие на карточке с отдельным confirm-модалом, не спрятана внутри формы погашения.
- Контакты (`Person`) **не вынесены в отдельный раздел** — управляются модалкой «Контакты» прямо на `/debts`, плюс инлайн-добавление нового контакта в форме создания долга. Отдельная страница `/people` была и её убрали намеренно.
- Известный (исправленный) баг: страница `/debts` изначально не вызывала `jarsStore.fetchJars()`, из-за чего список копилок в форме долга был пуст при заходе напрямую на `/debts` — форма молча не давала сохранить. Уже исправлено, но если «форма долга не сохраняется» — первое, что проверять.

#### Массовое создание OWED_TO_ME на несколько контактов сразу

Сценарий: оплатил счёт, хочешь раскидать возврат на нескольких друзей одним действием (например, по 500 на каждого из 5).

- Только для `OWED_TO_ME` (форма долга «я должен» — по-прежнему один контакт). В `DebtCreateForm.vue` при этом типе `USelect` переключается в `multiple`, поле суммы — это **сумма с одного человека**, итог считается как `сумма × кол-во`.
- Копилки для списания выбираются **один раз на всю группу** (как обычно), не по отдельности на человека.
- Эндпоинт `POST /debts/bulk` (`CreateBulkDebtDto`, `DebtService.createBulk`) — принимает `entries: {personId, amount}[]` + `allocations: {jarId, amount}[]` (сумма аллокаций = сумма всех entries). Каждая копилка дебетуется **один раз** на свою долю общей суммы; у каждого созданного `Debt` при этом всё равно своя собственная `DebtAllocation[]` — это проекция общих jar-весов на сумму конкретного человека через тот же `proportionalSplit`, что и в `repay()`. Из-за независимого округления на человека возможен дрейф в пределах тиынов между суммой `DebtAllocation` по всем долгам и фактическим списанием с копилки — то же допущение, что и везде в проекте (`EPSILON = 0.01`), не считается багом.
- Одна запись в истории на всю пачку (`type: 'DEBT_CREATE_BULK'`, payload `{debtIds: string[], allocations}`), отмена одним действием удаляет все созданные `Debt` и возвращает деньги в копилки разом — **нельзя** отменить один долг из пачки отдельно через `/history/undo` (только целиком всю операцию, пока она последняя в истории).

### История (`HistoryAction`) и отмена

- Каждое денежное действие (доход, расход create/update/delete, перелив, долг create/repay/forgive) пишет строку в `HistoryAction` с `type`, человекочитаемым `summary` и JSON `payload`, достаточным для отмены.
- «Отменить последнее действие» (`POST /history/undo`) — берёт последний неотменённый `HistoryAction` пользователя и применяет **свой обработчик на каждый `type`** (`HistoryService` в `back/src/history/history.service.ts`). Это не event-sourcing и не глубокий откат — только последнее действие.
- Summary для долговых операций включает **разбивку по копилкам с именами** («Дали в долг 3 000 (Друг) — списано из: «Накопления» 1 000, «Нужды» 2 000») — добавлено по запросу, чтобы не гадать, откуда/куда ушли деньги. Суммы форматируются с пробелами (`toLocaleString('ru-RU')`).
- Правки логики долгов/списания **обязательно** держать синхронными между `DebtService` (что реально произошло) и `HistoryService.undoDebtRepayment`/`undoDebtCreate` (как это откатить) — они читают одну и ту же форму `payload`.
- UI истории (`history.vue`) — у каждого `type` действия свой цвет/иконка (жёстко заданы в `TYPE_META`), плюс фильтр-чипы по типам и переключатель «показывать отменённые».

### Статистика

- `GET /statistics/summary` — среднее в день считается как `total / daysInRange`, а `daysInRange` **не фиксированные 30 дней**: правая граница — сегодня, левая — `max(30 дней назад, дата первого расхода пользователя)`. Это специально исправлено — раньше у новых пользователей среднее было искусственно занижено (делилось на 30, даже если реальных данных был один день).
- Круговая диаграмма по копилкам использует `jar.color`, не generic-палитру (см. выше).

## Деньги — форматирование и ввод

- Отображение сумм — `formatMoney()` в `front/app/utils/format.ts`, `Intl.NumberFormat('ru-RU', {style:'currency', currency:'KZT', maximumFractionDigits:0})` → «1 000 000 ₸»-стиль с пробелами.
- **Ввод сумм — не `UInputNumber` из Nuxt UI.** Компонент обёрнут вокруг reka-ui `NumberField`, который форматирует значение **только по blur**, во время печати показывает сырые цифры без разделителей — это поведение примитива, через пропсы не настраивается (проверено чтением исходников `reka-ui/dist/NumberField/NumberFieldInput.js`). Поэтому написан свой `front/app/components/MoneyInput.vue` — обычный `UInput` с ручным реформатированием на каждый `input`-эвент и пересчётом позиции курсора. **Все денежные поля (доход, расход, перелив, долг, дневная норма) используют `MoneyInput`, не `UInputNumber`.** Поля процентов (`defaultPercent`, ручное распределение) — по-прежнему `UInputNumber`, группировка разрядов там не нужна.

## Backend — архитектура

- `LedgerService` (`back/src/ledger/ledger.service.ts`, `@Global()`) — единственная точка мутации баланса копилки (`adjustJarBalance`) и записи в историю (`logAction`), всегда внутри одной Prisma-транзакции. Все сервисы, двигающие деньги (Income/Board/Transfer/Debt), обязаны идти через него, а не через `prisma.jar.update` напрямую.
- Авторизация: JWT, глобальный `JwtAuthGuard` через `APP_GUARD`, маршруты помечаются `@Public()` для обхода (auth-эндпоинты, health-check в `AppController`). `@CurrentUser()` достаёт `{userId, email}` из токена. Изоляция данных между пользователями — на уровне сервисов (везде `where: { userId }`), не Postgres RLS.
- **Prisma 7, а не 6** — это меняет конфигурацию:
  - `datasource.url`/`directUrl` в `schema.prisma` **больше не поддерживаются**, коннекшн-строка живёт в `back/prisma.config.ts` (`defineConfig` из пакета `prisma/config`).
  - `PrismaClient` требует driver adapter в рантайме — используется `@prisma/adapter-pg` + `pg` (см. `back/src/prisma/prisma.service.ts`). Без адаптера клиент не создать.
  - Плюс архитектуры: нет нативного query-engine бинарника («no-rust-engine»), что упрощает деплой на serverless (Vercel) — не нужно подбирать `binaryTargets`.
- Модули (все под `/api/...`): `auth`, `user`, `jar`, `income`, `board`, `transfer`, `person`, `debt`, `history`, `settings`, `statistics`.
- Serverless-обёртка для Vercel — `back/api/index.ts`, переиспользует `createNestApp()` из `back/src/create-app.ts` (общий фактори и для `main.ts`, и для serverless-хендлера), кеширует инициализированное приложение между вызовами. Протестирована локально (см. историю сессии) — работает.
- Тестов (jest) нет — вместо этого вся бизнес-логика (особенно проценты, долги, undo) прогонялась через ручные `curl`-сценарии на реальной БД в процессе разработки. Если будешь писать формальные тесты — начинай с `LedgerService` и `DebtService`, там больше всего инвариантов.

## Frontend — архитектура

- Nuxt 4, `app/` директория (не старый `src/`/корневой стиль).
- Auth: JWT хранится в cookie через `useCookie('mm_token')` (стор `stores/auth.ts`), не localStorage — работает и в SSR. Глобальный `middleware/auth.global.ts` редиректит неавторизованных на `/login`. Плагин `plugins/auth.ts` на старте приложения проверяет токен через `GET /users/me` и разлогинивает при 401. **Важно:** `onResponseError` в `composables/useApi.ts` при 401 делает `navigateTo('/login')` **только на клиенте** (`import.meta.client`) — если сделать это внутри SSR-фетча `useAsyncData`, ловится гонка, которая ломает `data` в непредсказуемое нементальное состояние (был реальный краш `/history` из-за этого). Держи эту защиту при рефакторинге.
- Стор копилок — `stores/jars.ts`, единственный источник правды про копилки на фронте, с computed `spendingJars`/`savingsJars`. **Каждая страница, где нужны копилки, обязана сама вызвать `jarsStore.fetchJars()`** — стора не подгружается глобально, отсюда был баг с пустым списком на `/debts` (см. выше).
- Дизайн: тёмная тема по умолчанию (`colorMode: {preference:'dark', fallback:'dark'}` в `nuxt.config.ts`), акцент `primary: 'indigo'` (`app.config.ts`), направление — «премиальный тёмный fintech» (Mercury/Ramp-стиль), выбрано пользователем осознанно после пары уточняющих вопросов. Не менять на светлую/зелёную тему без запроса.
- Иконки — Lucide через `@nuxt/icon`/`i-lucide-*`. Осторожно с переименованиями: `more-vertical` в текущей версии набора называется `ellipsis-vertical` (сломанное имя тихо не рендерит иконку и не падает сборкой — проверяй `node -e "require('@iconify-json/lucide/icons.json').icons"` при сомнениях).
- Chart.js регистрируется один раз в `plugins/chartjs.ts` (`Chart.register(...registerables)`).

## Чего нет / известные ограничения

- Нет браузерного расширения Claude in Chrome в этом окружении — вся фронтенд-верификация делалась через `curl` по SSR-выдаче и чтение исходников компонентов, не через реальный клик по UI. Drag-n-drop на канбане и живое форматирование в `MoneyInput` не проверялись глазами.
- Нет формальных unit/e2e тестов — см. выше.
- Нет реального деплоя — только локальная проверка.
